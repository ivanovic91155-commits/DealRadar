# Deal Radar: маркетплейсы → Telegram

Приватный радар велосипедов под перепродажу в Праге. Приложение объединяет источники в один поток, фильтрует объявления, хранит ID в SQLite и присылает в Telegram только то, чего раньше не видело. Bazoš читается через официальный RSS. Для Cyklobazar добавлен HTML-адаптер, но площадка может закрывать серверные подключения проверкой Cloudflare — см. раздел ниже.

Срочный алерт приходит первым. Затем обычный Python-код определяет модель, ищет предложения **нового** велосипеда на Zboží.cz, проверяет поколение/год/размер колёс, вычисляет медиану минимум из трёх магазинов и показывает ссылки. OpenAI API не используется. Ошибка поиска цены не мешает получить объявление.

## Что уже работает

- несколько поисковых профилей Bazoš в одном потоке;
- общий адаптер Cyklobazar для выдачи велосипедов в Праге;
- фильтры по словам, стоп-словам и цене;
- дедупликация по ID объявления, в том числе после TOP-поднятия;
- SQLite-состояние и повторная отправка после временной ошибки Telegram;
- Telegram-карточка с названием площадки, фото, ценой, локацией, ссылкой и кнопками обратной связи;
- независимая проверка кнопок каждые 10 секунд, даже когда площадки опрашиваются раз в час;
- сбор меток `интересно / мимо / дорого / подозрительно` для будущего AI-скоринга;
- web-поиск новой розничной цены через отдельный адаптер Zboží.cz;
- строгий match-score: другая генерация, год, размер колёс, б/у, рама или запчасть не считаются точным совпадением;
- медиана только минимум из трёх разных магазинов, дедупликация и отсечение ценовых выбросов;
- кэш успешной оценки на 14 дней, неполного результата на 48 часов и технической ошибки на 1 час;
- опциональный Codex CLI только для классификации неоднозначных кандидатов, без поиска цен;
- безопасный первый запуск: одно тестовое объявление вместо спама всей текущей выдачей.

## Запуск сегодня

Требуется Python 3.11+. Установите данные часовых поясов (они нужны для
`Europe/Prague`, в том числе на Windows):

```bash
python3 -m pip install -r requirements.txt
```

1. В Telegram откройте `@BotFather`, выполните `/newbot` и сохраните токен.
2. Создайте локальные файлы:

   ```bash
   cp .env.example .env
   cp config.example.json config.json
   ```

3. Впишите токен в `.env`, откройте созданного бота и отправьте ему `/start`.
4. Узнайте ID чата:

   ```bash
   python3 -m deal_radar chat-id
   ```

   Скопируйте напечатанный `TELEGRAM_CHAT_ID` в `.env`.

5. Проверьте Telegram:

   ```bash
   python3 -m deal_radar telegram-test
   ```

6. На Bazoš настройте обычный поиск: велосипеды, индекс `110 00`, радиус и цену. Внизу выдачи нажмите `RSS` и вставьте полученный URL в `profiles[].rss_url` файла `config.json`. URL в примере уже отражает поиск `kolo`, Прага и радиус 50 км, но URL, скопированный из вашего поиска, надежнее. Поиск Cyklobazar задаётся отдельно в `cyklobazar_profiles[].url`; пример ограничен разделом велосипедов и Прагой.
7. Проверьте ленту без Telegram и без изменения состояния:

   ```bash
   python3 -m deal_radar preview --limit 10
   ```

8. Отправьте первое объявление:

   ```bash
   python3 -m deal_radar once
   ```

   В режиме `bootstrap_mode: send_latest` первый запуск пришлет только одну верхнюю позицию и пометит остальные текущие объявления просмотренными. Следующие запуски отправляют только новые ID.

9. Запустите постоянный опрос:

   ```bash
   python3 -m deal_radar run
   ```

Текущая настройка `poll_interval_seconds: 3600`: все включённые площадки проверяются в одном цикле раз в час. `feedback_poll_interval_seconds: 10` отвечает только за Telegram-кнопки и не создаёт дополнительной нагрузки на маркетплейсы.

## Как работает цикл и когда приходят сообщения

1. Раз в час приложение запрашивает каждый включённый профиль Bazoš и Cyklobazar.
2. Результаты приводятся к общей модели `Listing` и сортируются по времени публикации.
3. SQLite отбрасывает уже виденные пары `площадка + ID`; повторный TOP-подъём того же объявления не создаёт новое сообщение.
4. За один цикл отправляется максимум `max_notifications_per_run` (сейчас 10) новых карточек.
5. Карточка объявления уходит сразу. Затем максимум для `retail.max_enrichments_per_run` карточек (сейчас 3) выполняется поиск новой цены и отдельным ответом приходит медиана со ссылками.
6. Нажатия `Интересно / Мимо / Дорого / Подозрительно` проверяются каждые 10 секунд и сохраняются с правильной площадкой объявления.

Сообщение приходит только при новом ID, а не каждый час. Если новых объявлений нет, бот молчит. После остановки процесса не работают ни часовой сбор, ни кнопки — для постоянной работы нужен запущенный процесс или системный сервис.

## Статус Cyklobazar

`cyklobazar_profiles` уже поддерживает URL выдачи, цену, ключевые/стоп-слова, подпись локации и исключение старых TOP-объявлений. Парсер извлекает ID, ссылку, заголовок, описание, цену, локацию, относительное время и фото. Дубликаты ссылок внутри одной карточки объединяются.

Если Cyklobazar возвращает Cloudflare `403` или страницу `Just a moment`, адаптер выдаёт явную ошибку и не пытается обходить защиту. Остальные источники продолжают работать. Для стабильного production-подключения нужен один из разрешённых вариантов:

- публичный RSS/API или письменное разрешение площадки;
- собственный «Hlídací pes» Cyklobazar с последующей разрешённой пересылкой уведомлений;
- запуск с подключения, которое сайт допускает без браузерной проверки, при сохранении низкой частоты запросов.

## Facebook Marketplace (ScrapeCreators)

Третий источник объявлений рядом с Bazoš и Cyklobazar. У Marketplace нет ни RSS,
ни разбираемого HTML, поэтому выдача берётся через платный поисковый endpoint
ScrapeCreators: **один запрос — один credit**. Адаптер живёт в
[sources/facebook.py](deal_radar/sources/facebook.py) и выполняет тот же контракт
`fetch() -> list[Listing]`; дедупликация, SQLite, обогащение и Telegram остаются
общими.

**По умолчанию источник выключен** (`FACEBOOK_MARKETPLACE_ENABLED=false`). Ключ
читается только из окружения (`SCRAPECREATORS_API_KEY`) и не хранится в
`config.json`. Нет ключа — выключается ровно этот источник, с понятной строкой в
логе; Bazoš и Cyklobazar продолжают работать.

Профили задаются координатами и радиусом, а не ссылкой:

```json
{
  "name": "Facebook — велосипеды в Праге",
  "query": "kolo", "lat": 50.0755, "lng": 14.4378, "radius_km": 60,
  "expected_currency": "CZK", "min_price": 1000, "max_price": 100000
}
```

Что важно в устройстве:

- **Расход предсказуем.** Один запрос на активный профиль, `count=24`, одна
  страница, никаких detail-запросов. Следующая страница берётся только при
  `has_next_page` и в пределах `max_pages_per_profile`.
- **У источника собственный интервал.** Общий цикл проекта — 420 секунд, и на
  нём один профиль стоил бы 6171 credit в месяц, то есть весь запас за месяц.
  Поэтому Facebook опрашивается не чаще `min_interval_seconds` (по умолчанию
  1200 секунд, 20 минут): лишние циклы пропускаются молча и бесплатно, а профиль
  укладывается в **2160 credits в месяц** — из 6100 это ~2.8 профиле-месяца.
  Часовой интервал (3600) вернул бы это к 720 credits.
- **Повторы только для временных отказов.** `400/401/402/403/404` — без повтора,
  профиль пропускается; `429`, таймаут, сетевая ошибка и `5xx` — не более двух
  повторов с растущей паузой. Ошибка одного профиля не трогает ни другие
  профили, ни другие площадки, ни цикл.
- **Валюта не выдумывается.** Площадка присылает цену строкой («CZK3,000»,
  «$300»), кода валюты в ответе нет. Валюта читается из строки, ожидание профиля
  — только запасной вариант. Для крон заполняются и `price_amount`, и
  `price_czk`; для остальных валют `price_czk` остаётся пустым, Telegram
  показывает оригинал, а расчёт выгоды честно уходит в ручную проверку вместо
  того, чтобы посчитать доллары кронами.
- **Поле `amount_with_offset_in_currency` не используется.** Вопреки названию это
  не сотые доли: у карточки с ценой «CZK3,000» оно равно `14271`, то есть пересчёт
  в другую валюту. Как источник цены оно превратило бы велосипед за 3 000 Kč в
  велосипед за 142 Kč.
- **Углублённый разбор страницы объявления.** Поиск отдаёт только заголовок,
  цену и одну картинку — по такому входу AI не назовёт ни модель, ни
  характеристики. Поэтому у новых объявлений догружается страница
  (`detail_enabled`, +1 credit за карточку): оттуда приходят **описание, вся
  галерея фотографий, настоящий код валюты, дата публикации и атрибуты
  площадки** (Condition, Bicycle Type). Всё это уходит в AI Level 1 одним
  вызовом: до пяти кадров (`vision_max_images`), заголовок, описание и цена в
  валюте объявления. По одному кадру модель различает разве что велосипед и
  шлем; по раме, приводу и навесному с разных ракурсов — уже модельный ряд.
- **Догрузка ограничена с трёх сторон:** потолок за цикл
  (`max_details_per_run`, 8), потолок за сутки UTC (`max_details_per_day`, 40,
  счётчик переживает перезапуск) и сам факт, что объявление обогащается один раз
  в жизни. То, что уже отсеял дешёвый фильтр — запчасти, детские, «куплю» — не
  стоит ни одного credit. Реальный расход: ~2160 на поиски + число новых
  объявлений в месяц.
- **Дату публикации даёт только страница.** В выдаче поиска `creation_time`
  приходит пустым; после догрузки она появляется, и объявление снова получает
  бонус за свежесть. Без догрузки свежесть обеспечивает лишь серверный фильтр
  `date_listed=last_24_hours`.
- **Ключ не попадает в логи.** В строке цикла только профиль, статус, длительность,
  число карточек, `credits_charged` и `credits_remaining`; тело ответа при ошибке
  не логируется.

Ручная проверка одним запросом (тратит один credit, ничего не сохраняет и не
отправляет):

```bash
SCRAPECREATORS_API_KEY=... FACEBOOK_MARKETPLACE_ENABLED=true python -m deal_radar facebook-check --limit 5
```

## Идентификация модели по каталогу

Модель считается подтверждённой (`model_confirmed`) только тогда, когда она найдена в каталоге `deal_radar/data/bike_catalog.json`. Свободные слова после названия бренда моделью больше не становятся: обороты вида `po servisu`, `ve skvělém stavu`, `levně`, `rychle` вырезаются, и в таком случае модель остаётся пустой. Если бренд известен, а модель похожа на настоящую, но в каталоге её нет, она сохраняется как кандидат (`model_source: "tail"`) — уверенность ограничивается сверху, поэтому поиск цены нового велосипеда пропускается, а сделка уходит в `MANUAL_REVIEW`.

Каталог задаёт также электрические модели и детские линейки: `Haibike AllMtn` распознаётся как e-bike без слова «elektrokolo», `Woom 4` — как детский велосипед. Дополнительно e-bike определяется по моторам (`Bosch CX`, `Shimano Steps`, `Yamaha PW` и т. п.).

Настройки секции `identity` в `config.json`:

- `catalog_enabled` / `catalog_path`: включение каталога и путь к своему файлу (пусто — файл из пакета);
- `fuzzy_match_cutoff`: порог совпадения при опечатках в названии модели;
- `brand_score`, `confirmed_model_score`, `candidate_model_score`: вклад в уверенность;
- `unconfirmed_confidence_cap`: потолок уверенности для неподтверждённой модели;
- `deal_scoring.require_confirmed_model`: отправлять сделки с неподтверждённой моделью в ручную проверку.

Новые бренды и модели добавляются правкой JSON-каталога, код менять не нужно.

Модель ищется и в описании, а не только в заголовке: `Merida (modelová řada Juliet)` даёт подтверждённую модель `Juliet`, хотя в заголовке её нет. Размер рамы и размер колёс различаются по контексту вокруг числа — `vel. 16"` это рама, `na 26" kolech` это колёса, поэтому ростовка больше не подменяет диаметр колеса.

У Cyklobazar в списке отдаётся только обрывок описания, а характеристики живут на странице объявления, поэтому для новых объявлений она догружается: `cyklobazar_detail_budget` (по умолчанию 20 запросов за цикл, переменная `CYKLOBAZAR_DETAIL_BUDGET`). Первая же HTTP-ошибка обрывает догрузку до следующего цикла — при 403 от Cloudflare продолжать значит напрашиваться на бан. Счётчик в логах цикла — `cyklobazar_detail_fetches`.

## AI-анализ объявлений (Level 1, shadow mode)

Слой в `deal_radar/ai/` превращает текст объявления в строгий JSON через OpenAI
Structured Outputs: тип объявления, бренд и модель, характеристики, состояние и
дефекты, срочность продавца, риск-флаги и цитаты-подтверждения для ключевых
полей. Пошаговая настройка ключа — [docs/openai-setup.md](docs/openai-setup.md).

**По умолчанию слой выключен** (`ai.enabled: false`); `AI_ANALYSIS_ENABLED` — это
одновременно и переключатель, и kill switch. При `AI_SHADOW_MODE=true` результат
только сохраняется в `analysis_json` и в таблицы `ai_analysis_cache` /
`ai_call_log`, но **не влияет** ни на статусы сделок, ни на Telegram: воронка
цикла остаётся ровно такой же, какой была без AI.

Что важно в устройстве слоя:

- **AI не может выдумать модель.** Предложенные моделью бренд и модель
  прогоняются через тот же каталог этапа 1; подтверждением считается только
  попадание в `bike_catalog.json` (`catalog_confirmed_model`). Иначе результат
  помечается `ai_model_not_in_catalog`.
- **Дешёвый pre-filter** (`ai/prefilter.py`) отсекает до вызова API дубликаты,
  запчасти, детские велосипеды и объявления «куплю». Сюда же попадают вещи, у
  которых в заголовке есть «kolo», но велосипедом они не являются: детское
  кресло (`sedačka`), велотуфли (`tretry`), спиннинг-тренажёр, а также аксессуары
  «X na kolo». Отдельным списком идёт экипировка — `helma`, `přilba`, `brýle`,
  `rukavice`, `zámek`, `nosič`, `blatník`, `košík`, `pumpa`, `tachometr`: она
  срабатывает только тогда, когда в заголовке нет самого велосипеда, поэтому
  «Prodám kolo Trek + helma zdarma» остаётся велосипедом, а «Helma POC Axion» —
  нет. Фильтр намеренно **не** отбраковывает короткие объявления без модели и
  без цены — именно такие чаще всего и оказываются скрытой возможностью.
- **Зрение.** Первое фото объявления уходит в Level 1 вместе с заголовком и
  описанием (`AI_VISION_ENABLED`, по умолчанию включено). По картинке модель
  надёжнее отличает настоящий велосипед от аксессуара и опознаёт тип, когда
  текст пустой («Prodám kolo»). Модель зрения — основная (Luna); задаётся
  `OPENAI_VISION_MODEL`. Если фото модели не по зубам, вызов автоматически
  повторяется без картинки, и текстовый разбор не страдает.
- **AI может убрать явный не-велосипед.** Когда слой выведен из тени
  (`AI_SHADOW_MODE=false`), уверенный вердикт «это не велосипед» тихо снимает
  карточку с отправки (причина `ai_not_a_bicycle`). Строго в одну сторону:
  классификация может только **убрать** мусор, но не поднять статус и не тронуть
  цену. Порог уверенности — `AI_MIN_REJECT_CONFIDENCE` (0.75): пустой результат
  лучше спрятанного велосипеда. `AI_CAN_AFFECT_DEAL_STATUS` здесь **не**
  требуется: тот флаг разрешает AI влиять на статус сделки и на цену, а «это шлем,
  а не велосипед» — вопрос релевантности. Пока вердикт не применяется (слой в
  тени), в лог уходит WARNING с именем флага, который его держит.
- **Вердикт «не велосипед» ниже порога тоже не доходит до человека.** Жёсткое
  подавление требует уверенности ≥ 0.75; при меньшей AI Gate добавляет
  блокирующий риск `NOT_A_BICYCLE`, и карточка остаётся в базе, но не уходит.
  Два замка: `min_reject_confidence` убирает объявление совсем, `block_non_bicycle`
  просто не пускает его в Telegram.
- **Бренд и модель не-велосипеда отбрасываются.** У шлема POC Axion есть и бренд,
  и модель; если оставить их в разборе, карточка озаглавится «🚲 POC Axion», а
  рыночная оценка пойдёт искать аналоги несуществующего велосипеда. При
  `is_bicycle=false` поля идентичности обнуляются (`ai_identity_dropped_not_a_bicycle`),
  тип и признак электро остаются — они помогают человеку.
- **Не платить дважды.** Кэш по отпечатку `source + id + заголовок + описание +
  цена + фото` вместе с версией промпта, версией схемы и именем модели.
- **Дневной бюджет** считается по `ai_call_log` с полуночи UTC, поэтому
  переживает перезапуск. При исчерпании объявления сохраняются как `AI_PENDING`.
- **Отказ OpenAI не останавливает парсер**: ретраи с экспоненциальным backoff,
  переход на запасную модель, затем `AI_FAILED` — и цикл идёт дальше.
- **Приватность.** Телефоны, email и HTML вырезаются из текста перед отправкой,
  ссылка на объявление не передаётся; первое фото прикрепляется как изображение
  (`input_image`), а не как ссылка «сходи открой». В запросе стоит `store: false`,
  а в журнал вызовов не пишутся ни ключ, ни тело запроса.
- **Промпты версионируются** в `deal_radar/ai/prompts/<name>/<version>/`; смена
  смысла промпта — это новый каталог, а не правка существующего. Текущая версия
  — `v1.3.0`: в запрос уходит вся галерея объявления, а не одна обложка, и
  модели разрешено **читать** текст на самом велосипеде (наклейка на раме, имя
  на трубе, клеймо на переключателе) как обычное доказательство с цитатой в
  `evidence`. Узнанный «на глаз» логотип по-прежнему моделью не считается:
  не прочитал словами — значит `null`. Уверенность по фото ограничена 0.75
  против 1.0 для текста объявления.

Результат AI подставляется в карточку Telegram только там, где детерминированный
разбор ничего не нашёл: модель, размер рамы, диаметр колёс. Приоритет всегда у
каталога.

## AI-оценка цены перепродажи (Level 2)

Ценовой каскад имел две ступени: реальные аналоги с площадок и амортизация от
цены нового. Обе требуют HTTP-запросов и потому упираются в бюджет скрейпинга —
из 63 объявлений цикла оценку получало одно, у остальных графа цены была пустой.
Третья ступень запросов к площадкам не делает и закрывает этот разрыв.

Включается отдельно от Level 1: `AI_PRICE_ESTIMATE_ENABLED` (по умолчанию
выключено). Работает на `gpt-5.6-terra` — оценка цены это задача на рассуждение,
в отличие от извлечения фактов.

Что важно в устройстве:

- **Измерение сильнее оценки.** Если движок нашёл реальную цену, она и
  остаётся; ответ модели ложится рядом как второе мнение. Оценка заполняет
  пустоту, а не спорит с данными.
- **HOT на оценке не выдаётся.** Статус HOT читается как «ехать покупать», и
  на догадке модели он не присваивается — сделка упирается в INTERESTING с
  флагом `hot_blocked_by_ai_price`. Снимается через `AI_PRICE_ALLOW_HOT`.
  Финансовые пороги при этом не меняются: понижается только итоговый статус.
- **Всегда диапазон, а не число.** У модели нет живых данных чешского рынка,
  поэтому в карточке показывается `low – high` и явная пометка, что аналогов
  не нашлось.
- **Проверки вменяемости.** Ответ отбрасывается целиком, если цена выходит за
  абсолютные границы, отличается от запрашиваемой более чем в 8 раз в любую
  сторону или диапазон шире, чем в 2.5 раза. Лучше пустая графа, чем неверная
  цифра в расчёте выгоды.
- **Кэш по идентичности велосипеда, а не по объявлению.** «Merida Juliet 2018,
  хорошее состояние, 26″» стоит одинаково у любого продавца, поэтому ключ —
  бренд + модель + год + колёса + состояние. Объявления об одном велосипеде
  внутри цикла тоже группируются и стоят одного вызова. Когда модель
  неизвестна, ключ становится по-объявленческим — иначе один ответ про
  «непонятный велосипед» разошёлся бы по всем неопознанным сразу.
- **Скидка быстрой продажи** берётся из `market_pricing.quick_sale_discount`,
  а не у модели: второй независимый финансовый порог проекту не нужен.

Расход при 300 объявлениях в сутки — порядка **$0.5 в день**: платят только
различные комбинации модели и состояния. Счётчики в логах цикла: `ai_price_calls`,
`ai_price_cache_hits`, `ai_price_applied`, `ai_price_rejected`, `ai_price_cost_usd`.

Проверка одной оценки без Telegram и без записи в прод:

```bash
python -m deal_radar ai-price-check --fixture tests/fixtures/ai/trek_marlin.json
```

Модели по умолчанию: `gpt-5.6-luna` основная, `gpt-5.6-terra` запасная. Расход —
около $0.0008 на объявление. Явный ID обязателен: алиас `gpt-5.6` уводит на Sol,
который в 25 раз дороже.

Диагностика без изменения production-данных:

```bash
python -m deal_radar ai-check --live
```

```bash
python -m deal_radar ai-test-listing --fixture tests/fixtures/ai/trek_marlin.json
```

Внешний поиск аналогов, AI-проверка аналогов и Level 2 в этот этап не входят.

## AI Gate и приоритет уведомлений

Level 1 давно возвращал `hidden_opportunity`, `seller_urgency`, `listing_quality`,
`identity_confidence` и риск-флаги, но решение «показать объявление человеку» их
не читало: в Telegram уходил любой `MANUAL_REVIEW`, которому хватило свободного
слота, а таких большинство — рыночной оценки хватает не всем объявлениям цикла.
Модуль `ai_gate.py` превращает уже сохранённый разбор в два **разных** числа и
нового запроса к модели не делает.

**`analysis_priority_score` (0–100)** — стоит ли тратить на объявление платный
рыночный анализ. Считается до Market Price Engine и задаёт порядок в очереди
`select_lookup_candidates`; состав кандидатов не меняется.

```text
base 25
+ hidden_opportunity 30
+ seller_urgency HIGH 20 / MEDIUM 8
+ listing_quality HIGH 5 / MEDIUM 3 / LOW 0
+ identity ≥0.80 → 10, ≥0.55 → 5, иначе −5
+ полезные факты (≥3 полей) 5
− риск: minor 5, medium 15, severe 40 (потолок 40)
```

**`notification_priority_score` (0–100)** — стоит ли показывать объявление
человеку. Считается после оценки сделки; деньги, ROI, ликвидность и уверенность
берутся **готовыми** из этапа 2.2, новых финансовых формул здесь нет.

Что важно в устройстве:

- **Плохое объявление ≠ плохой велосипед.** `listing_quality=LOW` сам по себе не
  даёт ни отказа, ни заметного штрафа: небрежно оформленные объявления — самая
  интересная зона для перепродажи. Наказывается отсутствие информации вместе с
  отсутствием причины. «Prodám kolo, 8 000» получает 15, а «Scott kolo, 5000,
  model nevím, spěchá» — 70 при том же качестве текста.
- **`MANUAL_REVIEW` больше не уходит просто так — но только когда AI живой.**
  Карточка отправляется, если есть сильный сигнал (`hidden_opportunity`,
  `seller_urgency=HIGH`, ценовая аномалия) **или** `notification_priority_score ≥
  manual_review_min_score` (60). Категория сохраняется целиком: убирается шум
  внутри неё, а не она сама.
- **Без AI ворота не глушат `MANUAL_REVIEW`.** Спасение категории построено на
  `hidden_opportunity` и `seller_urgency`, а они приходят только из живого AI.
  Пока AI в тени или выключен, у объявления нет ни одного AI-сигнала — и ворота
  не имеют оснований прятать всю категорию (иначе в проде канал замолкает
  целиком). В этом случае `MANUAL_REVIEW` уходит в обычный отбор слотов
  (`select_deal_notifications` с `manual_review_reserved_slots`), как было до
  Session 1; причина в логе — `no_ai_signals_defer_to_slots`. Свою шумоподавляющую
  работу ворота начинают именно с `AI_SHADOW_MODE=false`. Ценовая аномалия AI не
  требует и поднимает карточку в любом режиме.
- **Качественный HOT не теряется.** Единственное, что останавливает HOT, —
  блокирующий риск (`possible_scam`, `possible_stolen_bike`). Порядок карточек
  по-прежнему начинается со статуса, а внутри статуса сортирует уже важность.
- **Ворота ничего не удаляют.** Непрошедшее объявление остаётся в базе с
  причиной (`telegram_gate_no_strong_signal`), числом и списком слагаемых — их
  видно в `analysis_priority_reasons` и `notification_reasons`.
- **Shadow-режим соблюдается.** Пока `AI_SHADOW_MODE=true`, поля Level 1 в
  ворота не попадают: работают только детерминированные данные сделки. AI-сигналы
  включаются вместе с `AI_SHADOW_MODE=false`.
- **Не-велосипед блокируется при любой уверенности.** Уверенный вердикт убирает
  объявление раньше, отдельным слоем (`AI_MIN_REJECT_CONFIDENCE`); всё, что ниже
  порога, ворота помечают блокирующим риском `NOT_A_BICYCLE` и просто не
  отправляют. Выключается через `ai_opportunity_gate.block_non_bicycle`.

Логи цикла: `AI_GATE listing=… score=… action=DEEP_ANALYSIS reasons=…` и
`TELEGRAM_GATE listing=… status=MANUAL_REVIEW notification_score=… action=SKIP
reason=no_strong_signal`. Счётчики воронки: `ai_gate_passed`, `ai_gate_skipped`,
`ai_gate_blocked`, `avg_analysis_priority`, `hot_sent`, `interesting_sent`,
`manual_review_sent`, `manual_review_suppressed`, `avg_notification_priority`.

Все веса и пороги — в `config.json` (`ai_opportunity_gate`,
`telegram_notification_gate`); главные вынесены в `.env.example`. Чтобы вернуть
прежнее поведение целиком, достаточно `TELEGRAM_NOTIFICATION_GATE_ENABLED=false`.

## Поиск цены нового велосипеда без OpenAI API

Модуль `bike_identity.py` извлекает бренд, модель, поколение, год, размер колёс, тип, аудиторию и electric-флаг. `price_sources.py` формирует несколько точных запросов к Zboží.cz, читает серверный `__NEXT_DATA__` и карточки конкретных предложений магазинов. `pricing.py` проверяет соответствие, оставляет максимум одно предложение от магазина, убирает дубли и выбросы и только затем считает медиану.

Результаты имеют статусы `success`, `cached`, `insufficient_data`, `ambiguous_model`, `model_discontinued`, `source_error`, `codex_unavailable` и `timeout`. При менее чем трёх точных магазинах процент выгоды не показывается.

Ручная проверка без Telegram и без изменения SQLite:

```bash
python3 -m deal_radar price-check \
  --title 'Trek Marlin 7 Gen 3 29" 2025' \
  --price 14900
```

Ограничения, которые намеренно видны в Telegram:

- если модель/год/комплектация из объявления не определяются, результат будет `ambiguous_model` или `insufficient_data`;
- медиана не показывается при менее чем трёх точных предложениях от разных магазинов;
- цена нового велосипеда — ориентир, а не прогноз цены перепродажи б/у;
- этап 2.2 использует `quick_sale_price` рынка б/у и ручные обязательные расходы; стоимость ремонта автоматически не придумывается.

### Необязательный Codex CLI fallback

Codex не нужен для основной работы. Он подключается только для кандидатов с match-score `0.70–0.84` и не получает задачу искать цены. Данные объявлений передаются как недоверенный JSON; запуск идёт через `codex exec --ephemeral --sandbox read-only` со строгой JSON Schema, очищенным окружением, timeout и лимитами вызовов.

Один раз выполните вручную:

```bash
codex login
codex --version
```

После успешного входа включите fallback в `config.json` (`retail.codex_enabled: true`) либо задайте `DEAL_RADAR_CODEX_ENABLED=true`. Путь можно переопределить через `CODEX_PATH`. Не копируйте `auth.json`, ChatGPT access tokens или cookies в проект. Если Codex недоступен, основной pipeline продолжит работу.

### Основные настройки retail

- `sources`: сейчас поддержан `zbozi`; новые площадки добавляются отдельными адаптерами;
- `min_comparables`: минимум `3` разных магазина;
- `exact_match_threshold` / `ambiguous_match_threshold`: пороги точного и неоднозначного совпадения;
- `success_cache_hours` / `insufficient_cache_hours` / `error_cache_hours`: TTL по статусам;
- `source_timeout_seconds` / `total_timeout_seconds`: лимиты времени;
- `max_parallel_requests`, `max_queries_per_source`, `max_product_pages`: ограничение нагрузки;
- `max_telegram_sources`: максимум ссылок в Telegram;
- `currency_rates_to_czk`: ручные курсы для будущих не-CZK источников; текущий Zboží.cz отдаёт CZK;
- `codex_calls_per_hour` / `codex_calls_per_day`: предохранители fallback.

## Оценка сделки — этап 2.2

После Market Price Engine этапа 2.1 модуль `deal_scoring.py` локально рассчитывает:

```text
базовое вложение = покупка + acquisition + logistics + platform fees
резерв риска = базовое вложение × 10%
полное вложение = базовое вложение + резерв
чистая прибыль = quick_sale_price этапа 2.1 − полное вложение
ROI = чистая прибыль / полное вложение × 100%
```

Новый поиск рынка при этом не запускается. Результат получает статус `HOT`,
`INTERESTING`, `MANUAL_REVIEW`, `LOW_PRIORITY` или `REJECT`, сохраняется с
компонентами `deal_score` и снимком порогов в `deal_evaluations`, а затем
показывается в существующей Telegram-карточке. Ручные обязательные расходы
хранятся в `deal_cost_overrides`; до их явного задания все три поля равны нулю.
Автоматической оценки ремонта нет.

Основные пороги находятся в `deal_scoring` файла `config.json`: резерв 10%,
HOT от 4 000 Kč и 20% ROI либо от 100% ROI, пограничный ROI 15%, минимальные
liquidity/confidence для HOT — 50/100. Веса `deal_score` по умолчанию:
profit 25, ROI 25, liquidity 20, confidence 15, condition 10, risk 5.
Все значения и списки детерминированных признаков состояния можно менять без
правки Python. Переменные из `.env.example` переопределяют главные пороги и
политику отправки; `QUICK_SALE_DISCOUNT_PERCENT` настраивает существующий
расчёт этапа 2.1, а этап 2.2 только читает готовую `quick_sale_price_czk`.

По умолчанию Telegram отправляет `HOT`, `INTERESTING` и `MANUAL_REVIEW`.
`LOW_PRIORITY` и `REJECT` сохраняются, но не отправляются.

## Настройка фильтров

Каждый объект `profiles` (Bazoš) и `cyklobazar_profiles` — независимый поиск, но результаты объединяются в общий Telegram-поток. Можно сделать отдельные профили для `elektrokolo`, `gravel`, `Trek`, `Specialized` или разных ценовых диапазонов.

- `require_any_keywords`: хотя бы одно слово должно быть в заголовке или описании;
- `exclude_title_keywords`: стоп-слова проверяются только в заголовке, чтобы описание комплектующих не выкинуло целый велосипед;
- `min_price_czk` / `max_price_czk`: локальная страховочная фильтрация; объявление без распознанной цены не отбрасывается;
- `max_enrichments_per_run`: предохранитель расходов на AI web-поиск.
